# Facilitator answers · Builder worksheets

## 1 · Fingerprints

1. **64** hex characters = 32 bytes = **256 bits**.
2. **No.** A hash always has the same length, whatever the input size.
3. **No.** There's no key and no way back. You could only *guess* inputs and
   compare, which is why short, predictable inputs (like passwords) need a slow,
   salted password hash rather than plain SHA-256.
4. Download pages (checksums), Git commit IDs, certificate fingerprints, SSH
   "fingerprint of the host key" prompts, Docker image digests.

## 2 · One shared key

1. **No.** `bad decrypt` comes from the padding check. With a wrong key there's
   about a 1-in-256 chance the padding happens to look valid, and you get
   garbage *without* an error. Plain CBC has no integrity check.
2. In CBC, flipping a bit in the IV (or previous ciphertext block) flips the
   same bit in the decrypted plaintext. The attacker only needs to know
   *where* the amount is, not the key. Same with CTR/stream modes without a MAC.
3. Because encryption without integrity lets attackers tamper undetected, and
   because CBC in TLS led to a decade of attacks (BEAST, Lucky13, POODLE).
   AEAD checks integrity *before* releasing any plaintext.
4. Typically 50–200× on a machine with AES instructions. 3DES is also limited by
   its 64-bit block size (Sweet32).
5. Key agreement ((EC)DH) or key transport (encrypting the key with the
   recipient's public key). TLS 1.3 only uses (EC)DHE.

## 3 · Key pairs, PEM & DER

1. `*.pub`, `ec.pub.der`, and the text files. **Not** `*.key`.
2. RSA-3072: 422 bytes; P-256: 91 bytes; Ed25519: 44 bytes. That's about 5–10×
   smaller for comparable security.
3. `ec.pub.der` is just `data`, and some versions of `file` label the PEM public
   key as "OpenSSH public key", which is wrong. Tools guess from the content, and
   extensions are only conventions. Look at the `BEGIN` line, or ask OpenSSL
   (`openssl storeutl -noout -text file`).
4. `ec.pub` from `ec.key`: **yes** (step 3 did exactly that). `ec.key` from
   `ec.pub`: **no**. That's the one-way property the whole system relies on.

## 4 · Sign & verify

1. **No.** Signatures don't encrypt.
2. It proves the file was signed with the private key belonging to
   `mallory.pub`, and has not changed since. It says **nothing** about whether
   `mallory.pub` is Alice's.
3. **Whose** key it is: that's what a certificate from a trusted CA (or a
   fingerprint checked out-of-band) provides.
4. **No.** Anyone with a copy could have signed. That's why key pairs should be
   generated by the party they identify, preferably where the key will be used
   (or in an HSM / smartcard).

ECDSA signatures vary in length (70–72 bytes, DER-encoded); Ed25519 signatures
are always 64 bytes; RSA-3072 signatures are 384 bytes.

## 5 · Bonus: your own CA

1. Sent: **`shop.csr`**. Received: **`shop.crt`** (and usually the CA certificate).
2. **`ca.crt`**. Safe to share; that's the point. But recipients should check
   its fingerprint through a trusted channel, because whoever controls the
   trust anchor controls trust.
3. **`ca.key`**. With it, anyone can issue valid certificates for *any* name
   that trusts this CA. Real CAs keep root keys offline in HSMs and sign with
   intermediates.
4. The certificate only has **Extended Key Usage = serverAuth**. For mTLS, the
   partner needs *their own* key pair and a certificate with **clientAuth**,
   from a CA your server trusts.
5. Browsers only trust CAs in their root store, and public CAs must validate
   domain control (for example via the ACME protocol). Browsers also require a
   SAN, which we did add.
